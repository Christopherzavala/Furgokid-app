## 1. Decisiones de diseño

1. **Cuenta de adulto:** Firebase UID identifica exclusivamente a la cuenta adulta en el producto. Perfil activo y token de servicio requieren elegibilidad adulta aprobada por backend.
2. **Límite de Firebase Auth:** un cambio local no puede impedir por sí solo que un cliente llame al endpoint público de registro de Firebase Auth. Para satisfacer “ningún menor obtiene cuenta/token” se necesita impedir las altas directas en el tenant, usar un flujo server-issued/custom-token o una función de bloqueo compatible y habilitada. Ninguna configuración remota se cambia desde este worktree. El cumplimiento de este requisito queda bloqueado para producción hasta evidencia de la configuración efectiva.
3. **Autorización de pasajero:** backend-only, por pasajero/servicio/finalidad y con estado explícito. Una relación declarada se conserva como `declared`; no se etiqueta como verificación oficial.
4. **Minimización:** no DOB completa por defecto; no correo, teléfono, dirección permanente, escuela/curso, foto, salud o perfil conductual del menor; ningún `specialNeeds` en requests, matches ni nuevos contratos.
5. **GPS:** una sola ubicación actual por match; cliente puede solicitar acciones, pero no decide propietario, match, estado ni permisos. Cleanup Admin debe ser idempotente.
6. **Propietario de conductor:** el cliente no puede cambiar `driverId`; reasignación futura requiere operación backend explícita, transaccional y auditable.
7. **Proveedor desconocido:** ningún dato personal se envía a un proveedor nuevo o no verificado. Config ausente/inconsistente desactiva transmisión opcional.

## 2. Actores, autoridad y datos

| Actor                       | Capacidades                                                                                                        | Límites                                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Adulto autenticado elegible | Administrar su cuenta y crear solicitudes; administrar pasajero únicamente mediante backend y autorización válida. | No editar rol, elegibilidad, aprobación de conductor, autorización activa ni asignación de conductor directamente. |
| Conductor adulto aprobado   | Ver los datos mínimos de servicios asignados; publicar ubicación únicamente durante match activo autorizado.       | No leer evidencia parental ni solicitudes/matches ajenos; no conservar ruta histórica.                             |
| Pasajero menor              | Ninguna identidad de autenticación ni sesión autónoma; sujeto de datos administrados por adulto.                   | Sin cuenta, credencial, token, chat propio, analítica ni perfil conductual.                                        |
| Soporte/operador autorizado | Acceso de excepción con finalidad, actor, motivo y auditoría.                                                      | No consulta masiva ni acceso habitual a evidencia sensible; autorización jurídica/política pendiente.              |
| Cloud Functions/Admin SDK   | Validar y ejecutar transiciones privilegiadas usando IAM mínimo.                                                   | Admin SDK omite Firestore Rules; cada callable valida Auth, objeto, rol, propiedad, estado y payload.              |

### Categorías operativas

- `adult_account`: email/UID, nombre de adulto, rol, teléfono adulto cuando necesario, estado de elegibilidad y timestamps.
- `passenger`: ID opaco por servicio, nombre de referencia opcional, banda de edad, adulto responsable y estado.
- `service_location`: datos necesarios para recogida/destino dentro del servicio; no perfil permanente.
- `current_location`: coordenadas temporales y timestamp en la única ruta canónica.
- `authorization_evidence`: relación declarada, finalidad, versiones de texto/aviso, aceptación, estado y prueba técnica opaca; no documento de identidad.
- `operational_metadata`: estados, asignación y capacidad de servicio.
- `privacy_request`: tipo de derecho, sujeto, solicitante, legitimación a comprobar, estado y respuesta.
- `security_audit`: evento/actor/recurso opacos, operación, estado/resultado y hora de servidor; sin payload personal.

Los campos marcados como sensibles o legales requieren aprobación antes de uso. F0.7 define nombres conceptuales; no fija rutas finales salvo GPS.

## 3. Esquema Firestore propuesto

### 3.1 `users/{adultUid}`

```text
displayName, email?, phone?, role, driverApprovalStatus?,
adultEligibility: { status, method, noticeVersion, recordedAt },
createdAt, updatedAt
```

- `adultEligibility`, `role`, `driverApprovalStatus` y timestamps de decisión son server-controlled.
- El cliente solo cambia una allowlist de perfil adulto; nunca puede cambiar UID, rol, aprobación, elegibilidad o datos de otro usuario.
- No añadir DOB. No inferir mayoría de edad de email verificado, rol `parent` ni sesión.

### 3.2 Pasajero limitado al servicio

```text
matches/{matchId}/passengers/{passengerId}
  referenceName?   // solo si es necesario para el servicio
  ageBand          // under_14 | 14_to_17
  responsibleAdultUid
  relationshipDeclared
  authorizationStatus
  createdAt        // serverTimestamp
```

- `passengerId` aleatorio/no semántico y no reutilizado para perfilar entre servicios, sujeto a revisión de Producto/Legal.
- No copiar pasajero a perfil `users`, ruta, analytics, notificación, Sentry o logs.
- No incluir colegio, DOB, teléfono/correo, foto, salud ni `specialNeeds`.
- Mantener los datos de recogida/destino en la solicitud/match; solo participante autorizado recibe el mínimo requerido.

### 3.3 Evidencia de autorización

```text
matches/{matchId}/passengers/{passengerId}/authorizations/{authorizationId}
  adultUid
  relationshipDeclared
  purposeCode
  privacyNoticeVersion
  authorizationTextVersion
  acceptedAt            // hora de servidor
  channel               // flujo y versión de app
  status                // pending|active|revoked|expired|rejected
  revokedAt?
  evidenceOperationId   // aleatorio/opaque
  reviewState?          // solo revisión excepcional controlada
```

- Cliente no puede crear, activar, revocar ni modificar evidencia directamente.
- La callable `createPassengerAuthorization` valida cuenta adulta/elegible, relación declarada, match/solicitud propia, texto y versiones vigentes, finalidad permitida, edadBand permitida y campos exactos.
- El estado pasa a `active` solo si el backend valida todas las precondiciones. Payload ausente, error de red, versión desconocida o respuesta parcial = no autorizado.
- Revocación requiere `revokePassengerAuthorization`; el backend registra `revokedAt`, bloquea uso posterior y ordena cleanup de tracking asociado cuando corresponda.
- No existe estado `verified_guardian` en el esquema sin mecanismo legal y evidencia aprobados.

### 3.4 Requests de derechos

```text
privacyRequests/{requestId}
  requesterUid
  subjectRef            // ID interno/opaque
  subjectType           // adult|passenger
  rightType             // access|rectification|erasure|opposition|portability|restriction
  scopeCode             // referencias, no copia de contenido personal
  representativeClaim?  // relación declarada pendiente de validar
  identityState         // pending|verified|rejected
  status                // received|review|blocked|in_progress|responded|rejected|closed
  assignedRole
  receivedAt, dueAt?    // dueAt se calcula con configuración revisada por Legal
  responseAt?, outcomeCode?, evidenceRef?
```

- Cliente puede solicitar crear una petición autenticada; solo backend/operador autorizado modifica estado o resultado.
- Nunca guardar documentos sensibles de identidad en este registro por defecto.
- Solicitud no verificada de un representante no libera, exporta ni elimina datos de menores.
- Bloqueo temporal y derechos aplicables se implementan según instrucción legal; una solicitud no genera eliminación inmediata automática.

### 3.5 Auditoría y política de retención

- `securityAuditEvents/{eventId}`: escritura server-only; campos allowlisted: actor UID adulto o pseudónimo de sistema, acción, entidad opaca, código de resultado, timestamp servidor, request correlation ID. Sin coordenadas, payload, nombre, teléfono, escuela, token o `specialNeeds`.
- Retención configurable por categoría como código/config local revisado, no documento editable por cliente. Cada valor permanece `TBD_LEGAL` hasta decisión jurídica. Si no hay política para una categoría, no se activa limpieza masiva automática.
- `accountDeletionRequests` y recibos existentes deben alinearse con la política aprobada; Auth al final después de datos, tokens y tracking.

## 4. Matriz de autorización

| Recurso/operación             | Adulto dueño                                    | Otro adulto | Conductor asignado                               | Admin/backend                                             |
| ----------------------------- | ----------------------------------------------- | ----------- | ------------------------------------------------ | --------------------------------------------------------- |
| Perfil de cuenta              | Lee y modifica allowlist propia                 | Denegado    | Igual                                            | Operación justificada, mínima y auditada                  |
| Elegibilidad/rol/aprobación   | Lectura limitada; no escritura                  | Denegado    | No altera aprobación                             | Escritura solo por flujo privilegiado aprobado            |
| Solicitud antes de asignación | Lee la propia; mutaciones de estado por backend | Denegado    | Denegado                                         | Valida transición                                         |
| Match activo                  | Lee mínimo de su match                          | Denegado    | Lee mínimo del match asignado y aprobado         | Valida/cambia lifecycle                                   |
| Pasajero                      | Gestiona por callables si autorización válida   | Denegado    | Lee solo mínimo operativo del match asignado     | CRUD privilegiado con validación                          |
| Evidencia de autorización     | Solicita; no crea/activa por SDK                | Denegado    | Denegado                                         | Solo callables/servicio; acceso soporte excepcional       |
| GPS `tracking/current`        | Lee si participante adulto autorizado           | Denegado    | Lee/publica si asignado, aprobado y match activo | Cleanup idempotente y transición autorizada               |

| Audit events                  | Denegado                                        | Denegado    | Denegado                                         | Append-only server-side; lectura privilegiada justificada |

Las Firestore Rules protegen las lecturas/escrituras por SDK cliente. Funciones Admin deben repetir las validaciones; Rules no son una frontera para Admin SDK. Consultas deben demostrar acceso permitido por Rules; no depender de filtrado post-query.

## 6. Máquina de estados

```text
AdultEligibility: pending -> eligible | rejected
Authorization: pending -> active -> revoked | expired
Authorization: pending -> rejected
PrivacyRequest: received -> review -> blocked? -> in_progress -> responded -> closed
PrivacyRequest: review -> rejected -> closed
Tracking: stopped -> active (solo autorización + match activo) -> stopped + current doc deleted
Match: pending -> active -> completed | cancelled (transiciones backend existentes, sujeto a auditoría)
```

- Sin transiciones implícitas ni fallback permisivo.
- `unknown`, documento ausente, rol desconocido, error de backend, error de red, claims vencidos o schema futuro no habilitan pasajero ni GPS.
- Revocar autorización produce denegación inmediata al siguiente chequeo backend; F0.12 verifica propagación y limpieza.
- Stop/logout de GPS elimina tracking actual según directiva, sin cambiar por sí mismo el estado del match.

## 7. GPS: contrato de no-historial

1. Única escritura permitida: `matches/{matchId}/tracking/current` por `set/update` (un documento sobrescrito); no colección `trackingPoints`, `locations`, `routes/history` ni subcolección de puntos.
2. Rules: participante adulto; conductor asignado y `approved == true`; match `active`; campos coordenadas/accuracy/time allowlist; no cliente elige UID/match.
3. Backend verifica actor, match, estado y autorización antes de publicar o limpiar. Admin SDK no puede confiar en Rules.
4. Errores, analytics, Sentry y notificaciones no reciben lat/lon/address. Logs contienen solo código y correlation ID no reversible.
5. Stop, logout, revocation, match terminal y account deletion borran `tracking/current`, cada uno con ruta idempotente.
6. Tests buscan todas las rutas y fallan si se introduce almacenamiento histórico, cola offline GPS persistente o payload geográfico en telemetría.

## 8. Retención, derechos y borrado

Se define el mecanismo, no los plazos. Todo `retentionDays` o fecha fija queda prohibido hasta que Legal/Producto aprueben el valor por categoría.

| Categoría              | Evento de inicio propuesto             | Acción al vencer                                   | Excepción/control                                         |
| ---------------------- | -------------------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| Cuenta adulta          | Cuenta cerrada o petición efectiva     | Borrar/anonymizar por política                     | Legal determina registros que se deben conservar.         |
| Pasajero               | Fin del servicio o revocación          | Suprimir identificador/atributos conforme política | No copiar a perfil histórico.                             |
| Request/match          | Estado terminal                        | Reducir/suprimir lo no requerido                   | Resolver disputa/obligación legal con acceso restringido. |
| GPS actual             | Stop/logout/revocation/terminal state  | Eliminar inmediatamente                            | No backup/log con coordenadas.                            |
| Evidencia autorización | Revoke/expiry/fin servicio             | Retener o eliminar según plazo aprobado            | Legal fija evidencia mínima/defensa y acceso.             |
| Logs/diagnóstico       | Timestamp de evento                    | Purgar/anonymizar                                  | Sin PII por diseño; plazo por seguridad.                  |
| Tokens push            | Logout, revocation, token invalidation | Revocar/eliminar                                   | No payload infantil.                                      |
| Backups                | Política versionada del proveedor      | Expirar/restaurar bajo control                     | Región/retención efectiva pendiente de proveedor.         |
| Solicitud de derechos  | Cierre documentado                     | Purgar/anonymizar tras plazo aprobado              | Mantener prueba mínima si se aprueba.                     |

El servicio de eliminación existente se debe probar por colección/subcolección y proveedor; borrar un documento Firestore no equivale a borrar subcolecciones. Fallo parcial conserva checkpoint y `in_progress`, no elimina Auth temprano y no marca finalización falsa.

## 9. Evaluación de impacto y proveedores

Tratamientos de mayor riesgo: ubicación en tiempo real, asociación adulto-menor, posible texto que revele necesidades médicas, push token, diagnósticos con contexto escolar, y uso de SDKs de publicidad/mapas. Antes de producción documentar para cada proveedor: entidad, rol jurídico, datos/campos, finalidad, país/región, subencargados, transferencias, acceso, contrato, retención, eliminación, seguridad e incidente. Datos/región desconocidos = integración desactivada para dato infantil.

No se declara completa una evaluación de impacto ni una base de licitud. Legal confirma si se requiere evaluación formal, su método y el tratamiento de resultados.

## 10. Plan de migración no destructivo

1. **Inventario:** enumerar colecciones/campos y rutas de escritura. No leer/exportar datos reales desde este entorno.
2. **Write fence:** primero rechazar nuevos `specialNeeds`/edad texto/DOB/campos de menor en Rules y Functions; conservar lecturas antiguas solo en superficies ya autorizadas hasta fecha aprobada.
3. **Dual contract:** si se necesita transición, escribir nuevo contrato versionado sin copiar campos sensibles. El servidor identifica versión explícitamente.
4. **Dry-run sintético:** contar fixtures sintéticos por estado, validar idempotencia/checkpoints, sin credenciales ni conexión remota.
5. **Históricos:** generar reporte de ubicación/categoría/cantidad y propuesta de bloqueo/supresión; no migrar ni borrar datos reales sin aprobación jurídica y autorización operativa.
6. **Rollback local:** revertir el release de app/backend sin aceptar de nuevo campos retirados ni habilitar acceso más amplio.
7. **Cierre:** evidencias de reglas, Functions, clients, logs, proveedores, backups y job de retención. Cada ruta presenta dueño/estado.
