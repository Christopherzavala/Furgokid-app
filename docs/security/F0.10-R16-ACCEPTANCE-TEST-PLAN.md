## Oráculo / criterios de fallo

- Un dato prohibido, evento duplicado, flag de otra finalidad, acceso cruzado, write/read tras revocación o success UI sin confirmación backend es FAIL y bloquea aceptación.
- Un test mock no prueba Rules, Auth real ni SDK del release; Emulator no prueba política de proveedor ni retención externa.
- La aprobación Legal/Producto es un gate humano separado y no puede sustituirse por cobertura o test verde.
- Bugs confirmados deben registrarse con severidad, requisito, evidencia mínima reproducible y responsable antes de cerrar el incremento.

## Orden de ejecución recomendado

1. Contrato/documentación aprobados por Producto, Legal y Arquitectura.
2. Unitarios puros de modelo/estado, validación de payload y no-regresión de defaults.
3. Firebase Functions Emulator + Firestore Rules Emulator para ownership, eligibility, idempotencia, estados y cleanup; proyectos demo aislados.
4. Pruebas de integración RN con Auth/Functions mock o Emulator y SDK de terceros sustituidos por espías; sin datos reales.
5. Verificación supervisada en dispositivo de permisos, stores, logout/stop y estado de background.
6. Revisión independiente de resultados y evidencia. Nunca realizar deploy ni tocar datos reales como parte de aceptación local.
