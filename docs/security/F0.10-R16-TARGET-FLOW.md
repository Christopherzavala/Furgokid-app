# F0.10 R16 — Flujo objetivo cliente–backend (propuesta)

**Naturaleza:** diseño para revisión; no aprobado ni implementado.
**Base:** worktree C, `recovery/integrate-backup` @ `e4f2d5ed98a0a4b0f1a2625c93caa09f42ec6e4a`; corte 2026-11-07.

## 1. Reglas de diseño

- El backend es fuente de verdad para elegibilidad del adulto y estado de la autorización. Un checkbox, SecureStore, AsyncStorage, rol cliente o respuesta cacheada no concede acceso.
- Cada propósito tiene estado, aviso y acción aislados. Ubicación, marketing, analytics, anuncios y operación de transporte no se habilitan como paquete.
- Si cuenta, elegibilidad, aviso vigente, vínculo pasajero, autorización o servicio no puede verificarse, no crear autorización ni exponer/escribir ubicación.
- Diseñar con el conjunto mínimo aprobado por Producto/Legal. F0.6 plantea ID aleatorio, alias si se necesita y banda de edad en vez de fecha completa (`F0.6-BASELINE-DECISIONS-AND-DATA-INVENTORY.md:69-79`); esta es una propuesta de minimización, no una decisión de necesidad jurídica.
- La pantalla actual de consentimiento parental no es fuente autoritativa: guarda localmente y no invoca los callables observados (`ParentalConsentScreen.tsx:97-121,171-185`; `functions/src/passengerAuthorizationCallables.js:10-52`).

## 2. Flujo propuesto

```mermaid
sequenceDiagram
  actor Adulto
  participant App as App autenticada
  participant Gate as Consent/Eligibility API (pendiente de contrato)
  participant Callable as onboardPassenger
  participant Auth as Firebase Auth
  participant DB as Firestore/Admin
  participant Rules as Firestore Rules
  participant Worker as Revocation cleanup worker

  Adulto->>App: abre alta de pasajero
  App->>Auth: comprueba sesión actual
  App->>Gate: obtiene elegibilidad, noticeVersion y estados por finalidad
  Gate-->>App: estado autoritativo; desconocido/error = bloquear y ofrecer reintento
  App->>Adulto: aviso versionado, transporte y campos mínimos aprobados
  Adulto->>App: acción afirmativa para alcance específico
  App->>Callable: passengerId, alias mínimo, purpose, notice/text versions, declaraciones
  Callable->>Auth: valida contexto autenticado
  Callable->>DB: transacción verifica rol/eligibility/versión/owner y estado previo
  DB-->>Callable: crea/actualiza registro mínimo y evidencia; devuelve status/id
  Callable-->>App: resultado confirmado; no habilitar tracking hasta refresh autoritativo
  App->>Rules: consulta autorizada/solicita acceso al flujo de match
  Rules-->>App: permite solo ownership/relación/estado vigente o deniega

  Adulto->>App: revoca propósito o autorización de transporte
  App->>Callable: retiro autenticado, objeto y operación idempotente
  Callable->>DB: estado terminal/registro de evento; deniega acceso nuevo inmediatamente
  Callable-->>App: `revoked` / resultado idempotente
  Callable->>Worker: cleanup pendiente
  Worker->>DB: elimina solo tracking actual autorizado y confirma cleanup
  App->>Gate: actualiza estados de permisos/proveedores elegibles por separado
```

El diagrama incluye APIs objetivo necesarias que no están implementadas en el cliente actual. Hoy solo están exportados `onboardPassenger`, `updatePassengerAuthorizationStatus` y un job horario; no se encontró callable cliente de lectura de elegibilidad/estado para pasajero (`functions/index.js:442-452`, `src` sin referencias a esos nombres). Las Rules permiten lectura de autorizaciones del propio guardian pero niegan escritura cliente y deniegan toda lectura/escritura de `authorizationEvents` (`firestore.rules:421-432`). No asumir que el móvil puede consultar el documento `passengers`: revisar sus reglas y consulta real antes de implementar.

## 4. Contrato objetivo pendiente de aprobación

Antes de INC-2/INC-4, Arquitectura debe proponer endpoints/consultas mínimos para:

1. `getPassengerAuthorizationState`: Auth UID del servidor; respuesta filtrada por ownership y propósito con estado, versión y timestamps mínimos; nunca devolver evidencia sensible por defecto.
2. `onboardPassenger`: definir idempotency key/request ID obligatorio, reutilización segura ante retry, deduplicación y límites de colisión; reconciliar estado existente en vez de generar evidencia duplicada. El payload exacto depende de decisión Legal/Producto.
3. `updatePassengerAuthorizationStatus`: permitir revocación por objeto explícito y autorización vigente; preservar latest authorization, registrar actor/time/purpose; respuesta `revoked` confirmada incluso si limpieza asíncrona sigue pendiente, con un `cleanupStatus` explícito.
4. Separar estado de autorización de transporte de permiso OS para obtener localización, permiso de background, autorización de compartir ubicación, marketing y analytics. Sus transiciones no se deben sincronizar con una única boolean.
5. Error/reintento: auth expirada renueva sesión; `failed-precondition` pide revalidar aviso/estado; `permission-denied` no reintentar automáticamente; error/red deja UI bloqueada y conserva el formulario mínimo sin marcar éxito; retry usa mismo idempotency key.

Esto es arquitectura propuesta; endpoint de lectura, esquema de idempotencia y política de retries aún no están en código y requieren revisión del responsable de Arquitectura. No alterar callable/Roles en R16.

## 6. Estados y recuperación

| Estado o condición                 | Decisión de cliente objetivo                                                                                                       | Condición de salida                                            |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Auth no disponible/expirada        | No iniciar; permitir reautenticación                                                                                               | Auth confirmada                                                |
| Elegibilidad desconocida/rechazada | No crear ni usar autorización                                                                                                      | Gate backend finaliza elegible, método/aviso trazables         |
| Notice version nueva               | No repetir automáticamente consentimiento anterior                                                                                 | Mostrar aviso vigente y guardar acción según contrato aprobado |
| Pendiente/error de callable        | No mostrar `active`; no habilitar tracking                                                                                         | Confirmación/consulta de servidor                              |
| Active                             | Usar solo para propósito y vínculo vigentes                                                                                        | Backend/Rules confirma en operación sensible                   |
| Revoked/expired/rejected           | Cortar accesos nuevos inmediatamente; detener tracking local en cuanto se procesa la revocación; limpieza server-side reintentable | Cleanup verificado por job; permisos OS revisados por separado |
| Sin red/estado desconocido         | No confiar en cache para acceso a datos sensibles o tracking nuevo                                                                 | Refresh backend satisfactorio                                  |
| Baja de cuenta                     | Solicitud separada, idempotente y con estado consultable; no simular borrado local como borrado remoto                             | Cada fase de borrado verificada según política aprobada        |
